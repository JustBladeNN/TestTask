# Task Lifecycle API

Minimal API на .NET 9: PostgreSQL хранит задачи, RabbitMQ получает событие после завершения.

## Запуск

1. Запустить PostgreSQL и RabbitMQ.
2. При необходимости изменить подключения в `appsettings.json`.
3. Выполнить `dotnet run`.

Схема БД создаётся через `EnsureCreated`, поэтому отдельный шаг с миграциями не нужен.

Проверка теста:

```powershell
dotnet test .\TaskLifecycle.Api.Tests\TaskLifecycle.Api.Tests.csproj
```

## API

- `POST /tasks` — создать задачу.
- `GET /tasks` — получить все задачи.
- `PUT /tasks/{id}/complete` — завершить задачу.
- `DELETE /tasks/{id}` — удалить задачу.

Пример создания:

```json
{
  "title": "Buy milk",
  "priority": "High"
}
```

## Решения

- HTTP-запрос не ждёт RabbitMQ: событие попадает во внутренний `Channel`, а отправляет его
  `BackgroundService`.
- Событие ставится в очередь только после успешного сохранения задачи.
- Если RabbitMQ недоступен, задача всё равно завершается, а потерянное событие попадает в лог.
- Конкурентные запросы контролирует PostgreSQL `xmin`. Первый `/complete` сохраняется, второй
  получает `409 Conflict`.
- При остановке writer закрывается, накопленные события дочитываются, затем закрываются канал и
  соединение RabbitMQ. Общий таймаут остановки — 5 секунд.
- API не возвращает служебный `xmin`: сущность БД и контракт ответа разделены.

Интеграционный тест поднимает API через `WebApplicationFactory`, заменяет PostgreSQL на in-memory
провайдер и RabbitMQ на `ITaskEventPublisher`. Он проверяет создание, завершение, одну публикацию
события и `409` при повторном завершении.

## Ограничения

Очередь событий находится в памяти, поэтому это доставка best effort. Для гарантированной доставки
следующим шагом был бы transactional outbox. `EnsureCreated` выбран только для компактного тестового
проекта; в рабочем сервисе использовались бы миграции.
